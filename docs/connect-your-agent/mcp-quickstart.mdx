The general SAC MCP server sits between your AI agent and your phone. The agent asks over MCP; the server stores the request and shows it to your paired phone; you decide on the phone; the agent reads the result. The server holds no key and cannot approve anything itself.

**What it can ask for:** an acknowledgement, a message signature, and a SOL or SPL-token transfer. There is no swap or staking tool on this server; staking has its [own server](/docs/skr-staking-server), and swaps and prediction orders come through [feeds](/docs/publish-feeds). Every tool is listed on [MCP tools](/docs/mcp-tools).

## Prerequisites \{#prerequisites}

- **Node 24.21 or newer** (the server uses the built-in `node:sqlite`), or Docker.
- **SAC on an Android phone**, with a wallet saved ([Connect your wallets](/docs/wallet-setup)) on the network your agent will use.
- An **MCP client** that speaks Streamable HTTP: Hermes, OpenClaw, Claude, or another.
- For transfers only: a Solana RPC endpoint for that network (`SOLANA_RPC_URL`).

## Step 1: Run the server \{#run-the-server}

Every setup needs two different random tokens: `MCP_TOKEN` for your agent and `PHONE_TOKEN` for the phone API. Generate each with `openssl rand -hex 32`.

<Tabs groupId="mcp-install">
<TabItem value="npm" label="npm package" default>

The server is published on npm as `@seekeragentconnect/mcp-server`, with the command `seeker-agent-connect-mcp`. Give it a config file and a data directory of its own:

```sh
mkdir -p ~/.seeker-agent-connect
cat > ~/.seeker-agent-connect/config.env <<'ENV'
MCP_SERVER_DATA_DIR=/home/you/.seeker-agent-connect
DATABASE_PATH=direct-server.db
SIDECAR_HOST=127.0.0.1
SIDECAR_PORT=8080
SIDECAR_PUBLIC_URL=http://127.0.0.1:8080
MCP_TOKEN=replace-with-a-random-token
PHONE_TOKEN=replace-with-a-different-random-token
MCP_ENABLED=true
MCP_DEMO_TOOLS=true
LIVE_COMMAND_TIMEOUT_SECONDS=60
REQUEST_TTL_SECONDS=86400
REQUEST_PENDING_LIMIT=100
PAIRING_TOKEN_TTL_SECONDS=600
SAC_SUPPORTED_NETWORKS=mainnet
ENV
chmod 600 ~/.seeker-agent-connect/config.env

npx --package=@seekeragentconnect/mcp-server -- \
  seeker-agent-connect-mcp --config ~/.seeker-agent-connect/config.env start
```

The server refuses to start half-configured and names what is missing. `npx` takes the newest release; `--package=@seekeragentconnect/mcp-server@0.0.1` pins one. Releases are published with provenance, so `npm audit signatures` verifies an installed copy.

</TabItem>
<TabItem value="docker" label="Docker">

The image `ghcr.io/seekeragentconnect/mcp-server` is public: no `docker login`, `linux/amd64` and `linux/arm64`. It listens on 8080 and keeps its SQLite database in `/data`:

```sh
docker run -d --name seeker-mcp \
  -p 127.0.0.1:8080:8080 \
  -v seeker-mcp-data:/data \
  -e SIDECAR_PUBLIC_URL=http://127.0.0.1:8080 \
  -e MCP_TOKEN=replace-with-a-random-token \
  -e PHONE_TOKEN=replace-with-a-different-random-token \
  -e MCP_ENABLED=true \
  -e MCP_DEMO_TOOLS=true \
  -e SAC_SUPPORTED_NETWORKS=mainnet \
  ghcr.io/seekeragentconnect/mcp-server:0.0.1
```

The named volume keeps the server identity, the pairing and every request across restarts; `docker stop` is a clean shutdown. Pin a version tag as above, or the image digest from the release notes on the source repository's [Releases](https://github.com/SeekerAgentConnect/sac/releases) page.

:::caution
The `compose/mcp` preset in the separate [`do-deploy`](https://github.com/SeekerAgentConnect/do-deploy) repository passes an explicit list of variables to the server, and `SAC_SUPPORTED_NETWORKS` is not on it yet. A server started from it declares no network, so an up-to-date phone signs nothing for it ([Declare the networks](#declare-networks)). Add the variable to the service's `environment` yourself, or run the image as above.
:::

</TabItem>
<TabItem value="source" label="From source">

From a checkout of the [source repository](https://github.com/SeekerAgentConnect/sac), with pnpm:

```sh
pnpm install --frozen-lockfile
cp .env.example .env          # set MCP_TOKEN and PHONE_TOKEN to two different values,
                              # and SAC_SUPPORTED_NETWORKS, e.g. mainnet
pnpm dev:mcp-server
curl http://127.0.0.1:8080/healthz   # {"status":"ok"}
```

The development `.env.example` turns on `MCP_DEMO_TOOLS`, which the first request below uses.

</TabItem>
</Tabs>

### Declare the networks \{#declare-networks}

`SAC_SUPPORTED_NETWORKS` is the list of Solana networks your server's manifest declares: comma-separated `mainnet`, `devnet` and `testnet`, lowercase, each at most once, or `none`. SAC offers only your wallets on those networks when you pair, and signs nothing for this server on any other.

It has **no default**. Unset or empty, the server declares no network, and an up-to-date phone shows the server but signs nothing for it: no message, no transfer. It is not read from `SOLANA_RPC_URL`; list the cluster that endpoint serves, plus any network you sign messages on. The startup log names the declared networks, or says there are none. Changing the list and restarting moves the manifest's revision, and the phone reads it again. More on [Declare the Solana networks you run on](/docs/direct-or-feed#supported-networks).

:::warning[Not a stdio server]
The server is a long-running HTTP service with MCP at `/mcp`. Do not put its command in an agent's MCP `command`/`args` fields; point the agent at the URL instead.
:::

**Expected result:** `http://127.0.0.1:8080/healthz` answers `{"status":"ok"}`.

## Step 2: Connect your agent \{#connect-your-agent}

Point your agent at `http://127.0.0.1:8080/mcp` with the header `Authorization: Bearer <MCP_TOKEN>`. Ready-made configurations for Hermes, OpenClaw, Claude and a generic client are on [Connect your agent](/docs/connect-your-agent).

**Expected result:** the agent lists the `vault_*` tools. Ask it to call `vault_get_capabilities`; it always answers.

## Step 3: Pair your phone \{#pair-your-phone}

Ask the agent to connect your phone. It calls `vault_create_pairing_link` and shows you a link; you open it on the phone and tap **Pair**. From a terminal, `seeker-agent-connect-mcp --config … pair` (npm), `docker exec seeker-mcp node servers/mcp-server/dist/cli.js pair` (Docker) or `pnpm pair` (source) prints the same code as a QR.

The details, including how the phone reaches a server on your computer, are on [Pair your phone and enable push](/docs/pair-your-phone).

After **Pair**, SAC opens the server's page with the wallet picker. Choose the wallet this server should use and tap **Use this wallet**.

**Expected result:** `vault_get_address` returns the address and network of the wallet you chose for this server. Another server paired with the same phone sees only its own choice.

## Step 4: Send a first request \{#first-request}

Start with a request that moves no funds.

<Tabs groupId="first-request">
<TabItem value="ack" label="Acknowledgement" default>

With `MCP_DEMO_TOOLS=true` (development only), ask the agent to call `vault_request_ack` with a short text, or from a source checkout:

```sh
pnpm agent ack "Deploy finished. OK?"
```

On the phone the request says **Acknowledge** or **Reject**. The wallet never opens.

</TabItem>
<TabItem value="sign" label="Message signature">

Ask the agent to call `vault_sign_message` with a short text and an `idempotency_key`, or from a source checkout:

```sh
pnpm agent sign "hello"
```

On the phone, tap **Approve and sign**, then confirm in Seed Vault Wallet. Signing a message moves no funds and works on any network your server declares.

</TabItem>
</Tabs>

**Expected result:** the tool answers at once with the request in state `PENDING`. That means stored, not seen and not approved. The request appears in the SAC Inbox.

## Step 5: Read the result \{#read-the-result}

Poll `vault_get_request` with the `request_id` until `terminal` is true:

```sh
pnpm agent get <request_id>      # the request as it is now
pnpm agent wait <request_id>     # keep reading until it settles, then print the outcome
```

| The agent reads | Meaning |
| --- | --- |
| `PENDING` | Waiting for you on the phone |
| `COMPLETED` | Acknowledged, or signed; the signature is in the result |
| `CONFIRMED` | A transfer landed on chain |
| `SUBMITTED` | A transfer was sent but is not confirmed yet. Not success |
| `REJECTED`, `CANCELLED`, `EXPIRED`, `FAILED` | Not done, and why |
| `UNKNOWN` | The wallet never reported. Never retry: the transaction may already be on chain |

To withdraw a request you no longer need, call `vault_cancel_request` while it is still `PENDING`. Every creating tool takes an `idempotency_key`; the same key returns the same request, so a retry never creates two. The full lifecycle is on [Protocol](/docs/protocol#lifecycle).

## Step 6: Enable push (optional) \{#enable-push}

While SAC is open, requests arrive live. To wake the phone when it is closed, register the server for the SAC relay and set `RELAY_URL`, `RELAY_SERVER_ID` and `RELAY_CREDENTIAL`. See [Enable push wake-ups](/docs/pair-your-phone#enable-push).

## Transfers \{#transfers}

`vault_transfer` asks the owner to send SOL or a classic SPL token. It is served only when `SOLANA_RPC_URL` is set, and the RPC endpoint must be on the network of the wallet the owner chose for this server, which must also be in `SAC_SUPPORTED_NETWORKS`; the server never chooses a network. Token-2022 tokens and NFTs are refused. Try it on devnet before mainnet.

## Hosting it \{#hosting}

A hosted server needs public HTTPS with HTTP/2 end to end, because live updates are a stream, and its hostname in `MCP_ALLOWED_HOSTS` if an agent reaches it by name. The Compose presets in the separate [`do-deploy`](https://github.com/SeekerAgentConnect/do-deploy) repository run the published image; their `compose.tls.yaml` overlay terminates TLS in the server itself on port 8443. Behind a platform that terminates HTTP/2 for you, set `SIDECAR_H2C=true` instead. The full runbook is `compose/README.md` in that repository.

## Troubleshooting \{#troubleshooting}

| Symptom | What to do |
| --- | --- |
| The server will not start and names a variable | Set it; every variable in the config above is required for the npm command |
| The agent gets `401` | The `Authorization` header does not carry `MCP_TOKEN` |
| `NOT_PAIRED` | Pair the phone ([Step 3](#pair-your-phone)) |
| `WALLET_NOT_CONNECTED` | Choose a wallet for this server on its page in SAC |
| The phone says the server hasn't declared its networks, or will not sign | Set `SAC_SUPPORTED_NETWORKS` (for example `mainnet`) and restart |
| `vault_transfer` is missing | Set `SOLANA_RPC_URL` |
| `vault_request_ack` is missing | It is a development tool; set `MCP_DEMO_TOOLS=true`, or use `vault_sign_message` |

Every error code is on [Errors and limits](/docs/errors-and-limits).
